# «Слушать вместе»: синхронизация Plastinka между устройствами

Свой протокол Plastinka, а не API Яндекса. Десктоп (Rust) и Android (Kotlin)
реализуют его независимо, поэтому всё, что идёт по сети, описано здесь
побайтно. Расхождение реализации со спекой — ошибка реализации или спеки, его
исправляют здесь, а не «как получилось».

Решения пользователя (2026-11-21): оба устройства играют один трек
одновременно; связь только по локальной сети; устройства равноправны;
при первой связи на обоих показывается одинаковый код, его подтверждают;
функция по умолчанию выключена; управление — кнопка «Устройства» в плеере и
раздел «Слушать вместе» в настройках. Зависимости десктопа: `mdns-sd` 0.22 и
`aws-lc-rs` напрямую (одобрено). Android — только системные API.

## 0. Правила проекта, которые здесь действуют

- **Звук между устройствами не передаётся.** По сети идут только команды,
  метаданные трека и позиция. Каждое устройство само берёт поток у Яндекса
  своим токеном (правило 1 — буфер только в памяти — не меняется).
- **Подписка проверяется на каждом устройстве.** Синхронизация доступна только
  на главном экране, то есть после успешной проверки Плюса; плеер создаётся
  как раньше, с `PlaybackPermit` (правило 2). Пришедшая по сети команда не
  создаёт плеер в обход проверки.
- **Токен Яндекса никуда не уходит.** Ни в mDNS, ни в рукопожатие, ни в
  сообщения. Секрет сопряжения — свой, хранится там же, где токен: keyring на
  десктопе, `EncryptedSharedPreferences` на Android. Хранилище недоступно —
  сопряжение не запоминается (код придётся подтверждать при каждой связи),
  в файл секрет не пишется.
- **Ответ Яндексу о прослушивании (`play-audio`) и обратную связь волны
  (`rotor feedback`) шлёт только ведущий** (см. §5), чтобы одно прослушивание
  не считалось дважды.
- Ошибки сети и битые сообщения не роняют приложение: соединение закрывается,
  пользователь видит понятный текст.

## 1. Термины

- **Устройство** — запущенная Plastinka с выполненным входом и Плюсом.
- **Идентификатор устройства** — 16 случайных байт, 32 символа hex в нижнем
  регистре. Создаётся один раз и хранится в конфиге (не секрет).
- **Связь** — установленное и проверенное соединение двух устройств. В версии 1
  у устройства не больше одной связи.
- **Ведущий (owner)** — устройство, чья очередь определяет, что играет.
  Второе — **ведомое**: играет тот же трек и подстраивает позицию.
  Ведущим становится устройство, на котором пользователь выбрал новый трек или
  список. Пауза и перемотка ведущего не меняют.
- **Часы** — монотонные миллисекунды устройства с любой точкой отсчёта
  (`Instant` на десктопе, `SystemClock.elapsedRealtime()` на Android).
  Это не время суток, сравнивать часы двух устройств напрямую нельзя (§4.2).

## 2. Обнаружение (mDNS / DNS-SD)

Пока функция включена и открыт главный экран (Android: приложение на экране
или идёт служба воспроизведения), устройство объявляет себя и ищет других.

- Тип службы: `_plastinka._tcp.local.`
- Имя экземпляра: имя устройства (§7), не длиннее 63 байт UTF-8. Android NSD
  при совпадении имён может дописать « (2)» — это нормально, устройства
  различаются по `id`.
- Порт: TCP-порт приёма соединений (§3). Сначала пробуем 47800, занят —
  любой свободный (порт 0), в объявлении — фактический.
- TXT-записи (все обязательны, значения ASCII):

| Ключ | Значение |
|---|---|
| `v` | `1` — версия протокола |
| `id` | идентификатор устройства, 32 hex |
| `acc` | метка аккаунта: первые 12 символов hex от `SHA-256("plastinka/1 account " + uid)`, где `uid` — числовой идентификатор аккаунта из `account/status` строкой в десятичной записи |
| `os` | `windows`, `linux`, `macos` или `android` |

- В списке показываются только устройства с `v=1`, тем же `acc` и другим `id`.
  Записи с пустым или неверным TXT пропускаем молча.
- Адреса: берём IPv4 из ответа (сначала частные диапазоны 10/8, 172.16/12,
  192.168/16, затем остальные; IPv6 в версии 1 не используем). Подключаемся по
  очереди к каждому, таймаут подключения 3 с.
- Метка `acc` видна всем в сети. Она не секрет и не защита: только отсев чужих
  аккаунтов. По ней можно подобрать `uid` перебором, это осознанный компромисс
  (выключено по умолчанию, решение пользователя).

**Подключение по адресу** — запасной путь, когда mDNS не проходит (брандмауэр,
гостевая Wi-Fi). В настройках устройство показывает свои адреса
`192.168.x.y:47800`, на другом их можно ввести вручную. Дальше всё как обычно.

## 3. Транспорт и рукопожатие

TCP. Каждое сообщение — **кадр**: 4 байта длины (big-endian, `u32`), затем
столько байт содержимого. Длина от 1 до 65536, иначе соединение закрывается.

Сторона, которая подключилась, — **инициатор** (`i`), принявшая — **ответчик**
(`r`). Первые три кадра — открытый JSON (UTF-8), дальше всё шифруется.

### 3.1. Открытые кадры

1. Инициатор → ответчик, `hello`:

```json
{"t":"hello","v":1,"role":"i","id":"<32 hex>","name":"<имя>","os":"windows",
 "acc":"<12 hex>","commit":"<base64>","known":true}
```

   `commit` = base64 (стандартный алфавит, с `=`) от
   `SHA-256(key || nonce)`, где `key` — открытый эфемерный ключ инициатора,
   `nonce` — 16 случайных байт (оба покажутся в кадре 3).
   `known` — у инициатора есть секрет сопряжения для `id` ответчика (взят из
   TXT `id`; при подключении по адресу — `false`).

2. Ответчик → инициатор, `hello`:

```json
{"t":"hello","v":1,"role":"r","id":"<32 hex>","name":"<имя>","os":"android",
 "acc":"<12 hex>","key":"<base64 65 байт>","nonce":"<base64 16 байт>","known":false}
```

   `known` — у ответчика есть секрет сопряжения для `id` инициатора.
   Перед ответом ответчик проверяет кадр 1: `v == 1`, `role == "i"`, `id` —
   32 hex и не свой, `acc` совпадает со своим. Не так — вместо `hello`
   шлёт открытый `{"t":"bye","reason":"version"|"account"|"busy"}` и
   закрывает соединение. `busy` — у ответчика уже есть связь или идёт
   сопряжение.

3. Инициатор → ответчик, `reveal`:

```json
{"t":"reveal","key":"<base64 65 байт>","nonce":"<base64 16 байт>"}
```

   Ответчик проверяет `SHA-256(key || nonce) == commit` из кадра 1.
   Не совпало — закрыть без ответа.

Обязательство `commit` нужно, чтобы посредник не мог подобрать свой ключ под
нужный код сопряжения: инициатор фиксирует ключ до того, как увидит ключ
ответчика, а ответчик отдаёт свой до того, как увидит ключ инициатора.

Поля, которых нет в описании, игнорируются. Проверка `hello` собеседника
(обе стороны, по шагам):

- битый JSON или не `hello` — закрыть без `bye`;
- `v != 1`, `role` не та, `id` не 32 hex в нижнем регистре — открытый
  `bye version`;
- `id` совпадает со своим (подключились к себе) — закрыть без `bye`;
- `acc` не свой — `bye account`;
- нет `commit` (у инициатора) или `key`/`nonce` неверной длины после base64
  (у ответчика) — закрыть без `bye`.

`name` очищается от управляющих символов, пустое — «Устройство», обрезается
до 64 символов. `os` — `[a-z0-9]{1,16}`, иначе считается `unknown`.
Длина строк везде в спеке — в символах Unicode (кодовых точках), не в байтах и
не в единицах UTF-16 (в Kotlin — `codePointCount`, а не `length`).

### 3.2. Ключи

- Кривая P-256 (secp256r1). Открытый ключ — SEC1 без сжатия, 65 байт
  (`0x04 || X || Y`). Общий секрет `Z` — 32 байта координаты X (так его отдают
  и `aws-lc-rs agree_ephemeral`, и Java `KeyAgreement("ECDH")`).
- `TH` = `SHA-256` от **байтов трёх кадров ровно как они ушли в сеть, вместе с
  4-байтовыми префиксами длины**, в порядке 1, 2, 3.
- HKDF-SHA256 (RFC 5869): `PRK = HKDF-Extract(salt = TH, IKM = Z)`, затем
  `HKDF-Expand(PRK, info, L)`:

| `info` (ASCII) | `L` | Зачем |
|---|---|---|
| `plastinka/1 i2r` | 32 | ключ AES кадров инициатор → ответчик |
| `plastinka/1 r2i` | 32 | ключ AES кадров ответчик → инициатор |
| `plastinka/1 sas` | 4 | код сопряжения: `u32` big-endian `mod 1000000`, 6 цифр с ведущими нулями, показ «123 456» |
| `plastinka/1 pair` | 32 | новый секрет сопряжения (если сопряжение подтвердят) |

### 3.3. Шифрованные кадры

AES-256-GCM. Nonce 12 байт: 4 нулевых байта и счётчик кадров этого
направления `u64` big-endian, начиная с 0 (первый шифрованный кадр в каждую
сторону — 0). AAD пустой. Содержимое кадра — шифротекст и 16 байт тега.
Открытый текст — JSON UTF-8 одного сообщения (§3.4, §4). Ошибка расшифровки,
повтор или пропуск счётчика — закрыть соединение. Счётчик дошёл до `2^32` —
закрыть (в жизни недостижимо).

### 3.4. Проверка: сопряжение или узнавание

Сразу после кадра 3 обе стороны знают оба `known`.

**Узнавание** (оба `known == true`). Каждая сторона первым шифрованным
сообщением шлёт

```json
{"t":"auth","mac":"<base64 32 байт>"}
```

где `mac = HMAC-SHA256(pair_secret, "plastinka/1 auth " || role || TH)`,
`role` — один байт `i` или `r` **отправителя**, `pair_secret` — сохранённый
секрет для этого устройства. Получатель сравнивает с ожидаемым (для роли
собеседника) за постоянное время. Не совпало — `{"t":"bye","reason":"auth"}`
и закрыть; в окне: «<имя> не узнало это устройство. Подтвердите код заново».
Секрет при этом не удаляется: его заменит только новое успешное сопряжение.

**Сопряжение** (хотя бы один `known == false`; оба знают оба флага, так что
режим у сторон всегда один и тот же — и та, у которой секрет есть, тоже
переходит к сопряжению, а её старый секрет заменит новый). Обе стороны показывают имя
собеседника и код из §3.2 и ждут решения пользователя (таймаут 120 с).
Пользователь нажал «Коды совпадают» — сторона шлёт `{"t":"confirm"}`.
«Отмена» или таймаут — `{"t":"bye","reason":"rejected"}` и закрыть.
Сопряжение состоялось, когда сторона и отправила свой `confirm`, и получила
чужой. Тогда она сохраняет секрет `plastinka/1 pair` под `id` собеседника
(заменяя старый) вместе с именем и ОС (§7).

Пока идёт проверка, других сообщений нет: всё, кроме `auth`, `confirm` и
`bye`, — повод закрыть соединение.

После проверки связь **готова**: обе стороны шлют начальный `state` (§4.4)
и начинают `ping` (§4.2).

## 4. Сообщения готовой связи

Шифрованный JSON с полем `t`. Неизвестный `t` и лишние поля игнорируются
(совместимость). Сообщение с верным шифром, но битым JSON или неверными
полями — пропустить, соединение не рвать.

### 4.1. Трек

```json
{"id":"12345","albumId":"678","albumTitle":"Альбом","title":"Название","version":"Live",
 "artists":[{"id":"9","name":"Исполнитель"}],"durationMs":215000,
 "coverUri":"avatars.yandex.net/get-music-content/…/%%","available":true,
 "warning":"explicit","loudness":{"integrated":-9.1,"truePeak":0.3}}
```

- `id` — обязательно, 1–64 символа `[0-9A-Za-z_-]`.
- `albumId`, `artists[].id` — `null` или 1–20 цифр.
- `albumTitle`, `title`, `version`, `artists[].name` — `null` или строка до
  512 символов;
  `artists` — не больше 20 элементов.
- `durationMs` — `null` или от 0 до 86 400 000.
- `coverUri` — `null` или шаблон с `%%` только из видимых символов ASCII
  (0x21–0x7e), который начинается с `avatars.yandex.net/` или
  `avatars.mds.yandex.net/`. Иное — считать `null`.
- `available` (по умолчанию `false`) и `artists` (по умолчанию пусто) можно
  не присылать; отправитель присылает всегда.
- `warning` — `null`, `"explicit"` или `"clean"`.
- `loudness` — `null` или два конечных числа.
- Что не прошло проверку (кроме `coverUri`) — весь `state` пропускается.

Это настоящий трек каталога, не его подмена FckCensor. Получатель решает сам,
что играть, своими плагинами (§5.4).

### 4.2. Часы

```json
{"t":"ping","n":17,"t0":123456789}
{"t":"pong","n":17,"t0":123456789,"t1":987654321}
```

`t0` — часы отправителя `ping`, `t1` — часы отвечающего в момент ответа.
Отвечать сразу. Получив `pong` в момент `t2` своих часов:
`rtt = t2 − t0`, `offset = t1 − (t0 + rtt / 2)` — на сколько часы
собеседника впереди своих (деление целочисленное, `rtt ≥ 0`). Храним
последние 8 замеров с `0 ≤ rtt ≤ 1000` и берём `offset` замера с наименьшим
`rtt`, при равных — самого свежего. Пока нет ни одного замера, связь для окна
ещё не готова: служба копит входящие `state`/`tick` и отдаёт их после первого
`pong` (§3.4 «готова» → первый `pong` → окно узнаёт о связи). Пинги: 5 штук через 200 мс после
готовности связи, затем каждые 3 с. Пинг шлют обе стороны — каждой нужна своя
оценка.

Перевод момента собеседника в свои часы: `local = remote − offset`.

**Живость:** каждая сторона шлёт хоть что-то не реже раза в 5 с (пинг это
обеспечивает). Ничего не пришло 15 с — связь потеряна.

### 4.3. Состояние

```json
{"t":"state","rev":42,"by":"<id>","owner":"<id>","track":{…}|null,
 "playing":true,"positionMs":61234,"at":123456789,"next":{…}|null,
 "shuffle":false,"repeat":"off","wave":false,"initial":false,"join":false}
```

- Все числа — целые без знака (`rev`, `positionMs`) или со знаком (`at`);
  отрицательные `rev`/`positionMs`, дробные и нечисловые значения — `state`
  пропускается. `by` и `owner` — всегда id устройства (32 hex), никогда не
  `null`: если ведущего нет (трека нет), `owner` — id отправителя.
- `rev`, `by` — версия: изменение с большей парой `(rev, by)` (сначала `rev`,
  потом `by` как строка) новее. Своё изменение: `rev = текущий + 1`,
  `by = свой id`. Принятое: `текущий = max(текущий, rev)`.
- `owner` — id ведущего.
- `track` — что играет, `null` — ничего.
- `playing` — должно звучать (не пауза).
- `positionMs` — позиция в момент `at` (часы **отправителя**). Позиция сейчас
  у получателя: `positionMs + (сейчас − (at − offset))`, если `playing`,
  иначе `positionMs`.
- `next` — следующий трек очереди ведущего (для показа), `shuffle`, `repeat`
  (`"off"`, `"all"`, `"one"`), `wave` — ведущий играет «Мою волну». Эти поля
  заполняет ведущий; ведомый, отправляя своё изменение (пауза, перемотка),
  копирует их из последнего принятого состояния.
- `initial` — начальное состояние после готовности связи (§4.4), `join` —
  только у инициатора, пользователь сам нажал «Подключить».

Получатель применяет `state`, только если `(rev, by)` новее текущей пары, и
только после начального обмена (§4.4).

```json
{"t":"tick","rev":42,"positionMs":62240,"at":123457795,"buffering":false}
```

Шлёт только ведущий, раз в секунду, пока играет, и сразу, когда после
запуска или перемотки звук пошёл. `rev` не меняется. Ведомый берёт из него
позицию для подстройки (§5.2) и игнорирует `tick` с `rev`, не равным текущему.

### 4.4. Начальный обмен

Ответчик шлёт начальный `state` (`initial: true`) сразу после готовности,
инициатор — тоже, со своим `join`. Каждое устройство описывает себя:
`rev` — свой счётчик, `by` — свой id, `owner` — свой id. Исключение —
**восстановленная связь** (§5.3, без `join`): там `owner` — ведущий, каким он
был до обрыва (если он был), даже если это собеседник. Получив чужой начальный
`state`, обе стороны одинаково выбирают, чьё состояние общее:

1. Трек есть только у одной стороны — её.
2. У обоих начальных состояний один и тот же `owner`, и это id одной из сторон
   (связь восстановилась) — её: ведущий остаётся ведущим, его очередь не
   теряется.
3. Трек у обеих, `playing` только у одной — её.
4. У инициатора `join: true` — ответчика (нажал «Подключить» — присоединяюсь).
5. Иначе — с большей парой `(rev, by)`; `by` у сторон разные, так что пары
   не совпадают никогда.
6. Трека нет ни у кого — общего состояния нет, ведущего нет.

Проигравшая сторона принимает выигравшее состояние как ведомая (§5.2).
Счётчик обеих — `max` из двух `rev`. Дальше — обычные `state`.

### 4.5. Прочее

```json
{"t":"command","action":"next"}
```

Ведомый → ведущему: `next`, `previous`, `shuffle`, `repeat`, `dislike`
(«Не нравится» в волне). Ведущий выполняет как свою кнопку (с её записями в
аккаунт и обратной связью волны), новое состояние уходит обычным `state`.
Пришло не ведущему (гонка) — игнорировать.

```json
{"t":"liked","track":"12345","liked":true}
```

Кто-то поставил или снял «Нравится» (запрос в аккаунт он уже сделал сам).
Получатель только обновляет своё сердце, в аккаунт не пишет.

```json
{"t":"bye","reason":"user"}
```

Перед закрытием: `user` (нажали «Отключить»), `shutdown` (выход, выход из
аккаунта, функцию выключили), `busy`, `version`, `account`, `auth`,
`rejected`.

## 5. Поведение плеера

### 5.1. Ведущий

- Играет свою очередь как раньше. Шлёт `state` при каждой смене трека, паузе,
  продолжении, перемотке, смене `shuffle`/`repeat` и при начале волны; `tick`
  раз в секунду.
- Конец трека, следующий по очереди — как раньше, новое `state`. Повтор
  трека («повторять трек») — тоже новое `state`: тот же трек с позиции 0,
  иначе ведомый остановится в конце.
- Ведомый прислал `state` (пауза, перемотка) — применить: пауза/продолжение и
  перемотка, если позиция расходится больше чем на 120 мс.
- `command` — как своя кнопка.

### 5.2. Ведомый

- Новый трек в `state` — запустить его с позиции «сейчас» (§4.3) плюс
  своя поправка задержки (§7). Тот же трек — пауза/продолжение и перемотка
  при расхождении больше 120 мс.
- **Подстройка по `tick`:** своя позиция сейчас — из последнего события
  плеера и прошедшего времени. Цель — позиция ведущего сейчас плюс поправка.
  Расхождение больше 120 мс в двух `tick` подряд — перемотка на цель. Не
  чаще раза в 4 с; не во время своей буферизации и 1,5 с после своего запуска
  или перемотки; не по `tick` с `buffering: true`.
  Исключение — **первый `tick` с `buffering: false` после нового трека или
  перемотки ведущего** (у ведущего звук только что пошёл, а ведомый стартовал
  по прикидке): если ведомый сам уже не буферизуется, расхождение больше
  120 мс исправляется сразу, без второго `tick` и без паузы 1,5 с. Если
  буферизуется — дальше по обычным правилам.
- Трек закончился у ведомого — ничего не делать, ждать `state` ведущего.
  Свою очередь он не продолжает.
- Трек не включился (нет в регионе, ошибка сети) — сообщение «Не удалось
  включить «…» на этом устройстве: …», связь не рвётся, ждём следующий
  `state`.
- Кнопки ведомого: пауза, продолжение, перемотка — своё изменение `state`
  (позиция — синхронная, по §4.3); «Следующий», «Предыдущий», перемешивание,
  повтор, «Не нравится» в волне — `command` ведущему; выбор трека или списка,
  запуск волны — устройство становится ведущим (`owner` = свой id, своя
  очередь). Медиаклавиши, системный плеер и мини-плеер — как кнопки окна.
- Ведомый не шлёт `play-audio` и обратную связь волны, Slopless у него
  ничего не пропускает автоматически; в свою локальную историю трек пишет.
- Очередь ведомого в окне: текущий трек и «Далее» — `next` ведущего.

### 5.3. Разрыв

«Отключить», выход, потеря связи (§4.2): каждое устройство продолжает играть
то, что играло, как своё; ведомый доигрывает текущий трек и останавливается
(своей очереди у него нет). Сообщение «Связь с <имя> разорвана».

Связь, которая оборвалась сама (не «Отключить» и не выход), восстанавливается
автоматически в течение 10 минут, пока устройство видно в mDNS: подключение
без `join`, сопряжённым устройствам код не нужен.

### 5.4. Плагины

Ведомый применяет к пришедшему треку свои плагины, как к своему: подмены
FckCensor, копии из других релизов, explicit-версии. Своего файла
пользователя у другого устройства нет, поэтому там звучит то, что даст его
FckCensor (или оригинал). Громкость, эквалайзер, качество и нормализация у
каждого устройства свои и не синхронизируются.

## 6. Ошибки и крайние случаи

| Случай | Что делаем |
|---|---|
| Брандмауэр не пустил входящие | Подключаться может только этот ПК (исходящие разрешены); в настройках подсказка про брандмауэр и подключение по адресу |
| Разные версии протокола | `bye version` → «Обновите Plastinka на <имя>» |
| Разные аккаунты (по адресу) | `bye account` → «На <имя> другой аккаунт Яндекса» |
| Уже есть связь | `bye busy` → «<имя> уже связано с другим устройством» |
| Код не подтвердили | `bye rejected` → «Сопряжение отменено» |
| Забыли устройство на одной стороне | Узнавание не пройдёт (`auth`) → предложение подтвердить код заново |
| Одновременное подключение друг к другу | Остаётся соединение, инициатор которого с меньшим `id` (сравнение строк); второе закрывается без `bye` |
| Битый кадр, длина вне 1–65536 | Закрыть соединение |
| Обе стороны меняют одновременно | Побеждает большая пара `(rev, by)`, проигравший догоняет следующим `state` |
| Ведущий буферизуется | Ведомый не подстраивается, пока `tick.buffering`; потом догоняет перемоткой |
| Нет Плюса / токен не принят | Синхронизация не запускается: главного экрана нет |

## 7. Что хранится

| Что | Где | Секрет |
|---|---|---|
| Включено ли, имя устройства, поправка задержки (−500…+500 мс, по умолчанию 0) | конфиг / `Prefs` | нет |
| Идентификатор устройства | конфиг / `Prefs` | нет |
| Список сопряжённых: id, имя, ОС | конфиг / `Prefs` | нет |
| Секрет сопряжения на каждое устройство (32 байта, base64) | keyring (`plastinka`, учётная запись `sync-<id>`) / `EncryptedSharedPreferences` | да |

Имя устройства по умолчанию: десктоп — имя компьютера, Android —
`Build.MODEL`. «Забыть» удаляет запись и секрет только на этом устройстве.

## 8. Тестовые векторы

Посчитаны десктопной реализацией (тест `spec_vectors` в
`src/sync/handshake.rs`); `TH`, ключи и код сверены независимо скриптом на
Python (`hashlib`, `hmac`). Android проверяет свою реализацию на тех же
значениях. Векторы меняются только вместе со спекой.

Исходные данные. Скаляры P-256 — по 32 байта: инициатор `0x11` × 32,
ответчик `0x22` × 32. Nonce: инициатор `0xa1` × 16, ответчик `0xb2` × 16.

`id` `1111…1111` (32 знака), имя `Plastinka PC`, ОС `windows`; ответчик —
`id` `2222…2222`, имя `Телефон`, ОС `android`; `acc` у обоих `0123456789ab`;
`known` у обоих `true`.

## 9. Что проверить вживую

- mDNS между Windows и Android NSD в одной Wi-Fi; при включённом Radmin VPN
  или другом виртуальном адаптере.
- Запрос брандмауэра Windows при первом приёме соединения; macOS — запрос
  «Локальная сеть».
- Насколько точно совпадает звук (на слух, проводные наушники и Bluetooth),
  нужна ли поправка задержки и порог 120 мс.
- Не начинает ли Яндекс отказывать в потоке при одновременной игре с одного
  аккаунта (`download-info`, `get-file-info`).
- Android в фоне с выключенным экраном: держится ли связь, не рвётся ли Wi-Fi
  в режиме энергосбережения.
