# Android, этап «Коллекция»: спецификация API

Охватывает шаги 1–3 (хаб и плейлисты, альбомы и исполнители, «История» и
«Недавнее»). Основа — наша десктопная спека `docs/api/stage-7.md` (раздел
«Коллекция пользователя»), `docs/api/stage-9.md` (история) и код
`src/api/catalog.rs`, `src/api/history.rs`. Живых запросов для этой спеки не
делалось: всё ниже опирается на те проверки, что уже сделаны для десктопа.

## Общее

- База: `https://api.music.yandex.net`. Заголовки у всех методов:
  `Authorization: OAuth <токен>`, `X-Yandex-Music-Client: YandexMusicAndroid/24023621`
  (в Kotlin это `YandexApi.get`/`post`). Токен не попадает ни в URL, ни в
  тексты ошибок.
- `uid` берётся из `account/status` (`AccountInfo.uid`).
- Ответ почти везде завёрнут в `{"result": …}`. 401/403 — `UnauthorizedException`
  («войдите заново»), остальные не-2xx — `IllegalStateException("сервер ответил N")`.
- Идентификаторы из ответа попадают в адрес следующего запроса, поэтому
  `uid`, `kind`, `id` альбома и исполнителя — только цифры.
- Разбор мягкий: нет поля — значение по умолчанию, непонятный элемент списка
  отбрасывается, остальные остаются.

## 1. Свои плейлисты

`GET /users/{uid}/playlists/list`

- Ответ: `{"result":[Playlist, …]}`, плейлисты без треков.
- Нужные поля Playlist: `uid` (или `owner.uid`), `kind`, `title`, `trackCount`,
  `owner.name`/`owner.login`, обложка. Нет `uid`, `kind` или `title` — элемент
  пропускаем.
- Обложка: `cover.uri` (шаблон с `%%`, после него бывает `?версия`) при
  `cover.type == "pic"`; при `"mosaic"` — первый из `cover.itemsUri`; запасной —
  `ogImage`. Нет — заглушка. URL: `https://` + uri с `%%` → `300x300`.
- Плейлист `kind == 3` — «Мне нравится», в список плейлистов не включаем
  (у него свой раздел).
- Пример:
  `{"uid":42,"kind":1001,"title":"Утро","trackCount":32,"owner":{"uid":42,"login":"x"},"cover":{"type":"mosaic","itemsUri":["avatars.yandex.net/…/%%"]}}`

## 2. Понравившиеся плейлисты

`GET /users/{uid}/likes/playlists`

- Ответ: `[{"timestamp":"…","playlist":Playlist}, …]`; разбор принимает и
  «голый» Playlist. Поля те же. Свежие первыми (сортировка по `timestamp`,
  строка ISO 8601).
- Дубли со «своими» (тот же `uid`+`kind`) убираем.
- Это дополнение: ошибка этого запроса не должна ронять список (показываем
  свои), ошибка обоих — ошибка экрана.

## 3. Плейлист с треками

`GET /users/{owner}/playlists/{kind}` (в `YandexApi.playlistTracks` уже есть)

- Ответ: `{"result":{uid, kind, title, trackCount, durationMs, cover, tracks:[{"id","timestamp","track":Track}]}}`.
- Без `track` у элемента (очень большие плейлисты, `richTracks=false`)
  остаются только `id` и `albumId`: такие треки догружаются `POST /tracks`
  (`YandexApi.tracks`).
- Ошибки: 404 `playlist-not-found`, 410 `playlist-is-deleted` → «Плейлист
  удалён или недоступен»; чужой закрытый — 403 (в нашем `get` это
  «войдите заново», на экране плейлиста формулировать нейтрально).
- Недоступные треки (`available != true`) в Android сейчас отфильтровываются
  в `playlistTracks`; для экрана плейлиста их стоит показывать серыми (шаг 2
  решит). В шаге 1 используем существующую фильтрацию.

## 4. Лайкнутые альбомы

`GET /users/{uid}/likes/albums?rich=true`

- Ответ: `[{"timestamp":"…","album":Album}, …]` (или голый Album).
- Нужные поля Album: `id`, `title`, `version`, `year`, `type`
  (`single`/`compilation`/иначе альбом), `artists[].name`, `coverUri`,
  `trackCount`, `available`. Нет `id` или `title` — пропускаем; `error` у
  элемента — пропускаем.
- Шаг 1: нужно только число — `result.size` после разбора.
- Без `rich=true` ответ — короткие ссылки `{id, albumId}` без названий;
  для количества этого хватило бы, но список (шаг 2) нужен с `rich=true`.

## 5. Лайкнутые исполнители

`GET /users/{uid}/likes/artists?with-timestamps=true`

- Ответ: `[{"timestamp","artist":Artist}, …]` или `[Artist, …]`.
- Поля Artist: `id` (число или строка), `name`, `cover.uri` (или `ogImage`),
  `counts.tracks`, `counts.directAlbums`. Нет `id` или `name` — пропускаем.
- Шаг 1: нужно только число.

## 6. Альбом с треками (шаг 2)

`GET /albums/{id}/with-tracks`

- Ответ: Album + `volumes:[[Track,…],…]` (диски; склеиваются по порядку).
- Неизвестный id: 200 с `error:"not-found"` и без `title` — «Не найдено».
  Нечисловой id: 404.
- Длительность альбома — сумма `durationMs` треков.

## 7. Исполнитель (шаг 2)

- `GET /artists/{id}/brief-info` — `result.artist` (`id` строкой, `name`,
  `cover.uri`, `counts`), `popularTracks:[Track]`, `albums:[Album]` (первые 9),
  `stats.lastMonthListeners`. Неизвестный — 200 с `artist.error`.
- `GET /artists/{id}/direct-albums?page=0&page-size=100&sort-by=year` — все
  альбомы: `{"pager":{"total":N},"albums":[Album]}`; листать, пока не набрали
  `total` (не больше 10 страниц).
- `GET /artists/{id}/tracks?page=N&page-size=100` — все треки,
  `{"pager":{…},"tracks":[Track]}`; страница за концом — 200 без `tracks`.

## 8. История прослушиваний (шаг 3)

`GET /music-history?fullModelsCount=50`

- **Формат пересказан по справке MarshalX, вживую не проверен.**
- Ответ: `{"result":{"historyTabs":[{"date":"2026-11-12","items":[{"context":{"type":"album|artist|playlist|wave|…","data":{"itemId":…,"fullModel":…}},"tracks":[{"type":"track","data":{"itemId":{"trackId","albumId"},"fullModel":Track}}]}]}]}}`.
- Полные модели только у первых `fullModelsCount` треков; у остальных только
  `itemId.trackId` — догружаем `POST /tracks` пачками.
- Контекст: `album` (`itemId.id`/`fullModel.id`, `title`), `artist` (`name`),
  `playlist` (`itemId.uid`, `itemId.kind`, `fullModel.title`), `wave`, иное —
  подпись из `fullModel.title`/`name`.
- Ограничения как на десктопе: не больше 30 дней и 300 треков. Всегда
  10 последних дней, параметры периода не работают.
- Плотно забит «Моей волной»: для блока «Недавнее» (альбомы и плейлисты из
  контекстов) историю брать с отбрасыванием `wave`.
- Ошибка/пустой ответ: блок «Недавнее» просто не рисуется.

## 9. Топ месяца (шаг 3)

Два новых адреса. Заголовки те же, что у остальных запросов музыки:
`Authorization: OAuth <токен>` и `X-Yandex-Music-Client`; параметров нет.
**Ответ без обёртки `result`** (как у `landing-blocks`): объект с массивом
в корне. Разбор терпимо смотрит и в `result`, если он вдруг появится.

- `GET /personal/top/artists/month` — исполнители:
  `{"artists":[{"artist":{Artist},"listenTimeSeconds":13110,"top":{"position":1,"progress":"up"}}]}`.
  Читаем: карточку исполнителя (`parseArtistCard`: `id` числом, `name`,
  `cover.uri`), `top.position` (место), `top.progress` (`up`, `down`, `same`,
  `new`; другое значение или нет поля — значка нет), `listenTimeSeconds`
  (нет — 0, подпись времени не показывается). Элемент без годной карточки
  пропускается. Сервис отдаёт не больше пяти исполнителей.
- `GET /personal/top/tracks/month` — треки:
  `{"tracks":[{"track":{"track":{"id":69810,"title":…},"artists":[…],"album":{…}},"playCount":8}]}`.
  Читаем только `track.track.id` (число или строка из цифр, иначе элемент
  пропускается: идентификатор идёт в тело `POST /tracks`) и `playCount`
  (нет — 0). Сами треки догружаются `POST /tracks` в порядке топа; трек,
  который не догрузился, пропускается вместе со своим числом. Не больше десяти.
- Страница «Топ месяца» — ошибка любого из двух запросов (или догрузки) это
  ошибка страницы с «Повторить»; оба списка пусты — «Послушайте музыку —
  здесь появится ваш топ за месяц.». Полка на хабе и в «Исполнителях»
  берёт только первый адрес; сбой полки не показывается, остальное работает.
- Источник в истории у треков топа — «Топ месяца» (`HistoryContext.Other`),
  как на десктопе.
- Подпись времени: секунды округляются до получаса; меньше часа — минуты
  («40 минут»), дальше «2 часа», «3,5 часа»; русские формы слов.
- Источники: десктоп `src/api/catalog.rs` (`top_artists`, `top_track_entries`,
  `fetch_month_top`), `docs/api/stage-7.md`. **На Android вживую не проверено.**

## 10. Полки коллекции (этап 1, шаг A)

Три адреса лендинга. Заголовки обычные (`Authorization: OAuth <токен>`,
`X-Yandex-Music-Client`). **Ответ без обёртки `result`**; разбор терпимо
смотрит и в `result`, если он вдруг появится. Любой сбой полки (сеть, 4xx/5xx,
не тот вид ответа) — полки нет, остальной раздел работает; прежний список
при повторной загрузке не стирается.

- `GET /landing-blocks/artists?count=16` — «Встречали в Моей волне».
  `{"items":[{"type":"artist_item","data":{"artist":{"id","name","cover":{"uri"}}}}]}`.
  Читаем `data.artist` через `parseArtistCard`; повтор исполнителя
  отбрасывается. Состав меняется от запроса к запросу (подборка).
- `GET /landing-blocks/new-releases?count=30` — «Новые релизы».
  `{"newReleases":[{"album":{"id","title","albumType","cover":{"uri"}},"artists":[{"id","name"}],"releaseDate":"2026-10-29T21:00:00+00:00"}]}`.
  У альбома `albumType` вместо `type` (`single`, `compilation`, иначе альбом),
  обложка в `cover.uri` (запасной `coverUri`), исполнители рядом с альбомом
  (запасные `album.artists`), год — первые 4 цифры `releaseDate`. Числа
  треков нет (0). Элемент без числового `id` или `title` пропускается,
  повтор альбома отбрасывается.
- `GET /landing-blocks/personal-playlists?count=10` — «Собираем для вас».
  `{"items":[{"data":{"playlist":{"uid","kind","title","cover":{"uri"}},"playlistType":"playlistOfTheDay","description":"Звучит по-вашему каждый день"}}]}`.
  Карточка плейлиста — тем же `parsePlaylistCard`, к ней добавляется
  `description` (поле `note`, показывается под названием в две строки).
  Плейлист открывается обычным `GET /users/{uid}/playlists/{kind}`. Только в
  «Плейлистах»: на вкладке «Волна» подборок нет (как на десктопе).
- Свои и понравившиеся плейлисты по-прежнему берутся из `playlists/list` и
  `likes/playlists` (разделы 1 и 2), но в `CollectionUi.playlists` они лежат
  одним списком с признаком `liked`: экран делит его на вкладки «Вы собрали»
  (`!liked`, без `kind` 3) и «Вам понравились» (`liked`). Понравившиеся
  плейлисты теперь, как и на десктопе, идут недавними первыми (`timestamp`).
- Раскладка (на десктопе число колонок зависит от ширины окна, на телефоне
  фиксировано): «Встречали в Моей волне» — 3 колонки × 2 ряда, «Новые
  релизы» и «Собираем для вас» — 2 колонки × 2 ряда. Не поместилось —
  «Показать все», раскрытая полка показывает всё и «Свернуть».
- Источники: десктоп `src/api/catalog.rs` (`met_artists`, `new_releases`,
  `personal_playlists`, `fetch_my_*`), `docs/api/stage-7.md`.
  **На Android вживую не проверено.**

## 11. «Все треки» исполнителя (этап 1, шаг B)

`GET /artists/{id}/tracks?page=N&page-size=100` (`page` с нуля; `id` только цифры,
иначе запроса нет и «Не найдено»). Заголовки обычные. Ответ в обёртке `result`:
`{"result":{"pager":{"page":0,"perPage":100,"total":219},"tracks":[Track]}}`, где
`Track` — тот же объект, что в `popularTracks` (`parseTrack`). Нечитаемый элемент
пропускается. `total` берём из `pager.total` (запасной `total` рядом), не меньше числа
пришедших.

- Страницы по 100 (как на десктопе, `ARTIST_TRACKS_PAGE`). Следующая страница
  запрашивается, пока `загружено < total` и последняя страница не пришла пустой
  (пустая страница, даже при большем `total`, — конец; считаем по числу элементов
  до отсева нечитаемых).
- Догрузка при прокрутке: хвост списка виден (последние 4 строки), страница ещё не
  грузится, прошлая догрузка не завершилась ошибкой. Одна страница дважды не
  запрашивается (флаг `loadingMore` и номер следующей страницы). Ответ после смены
  исполнителя отбрасывается (номер загрузки и ключ исполнителя). Повторы треков по id
  при добавлении страницы отбрасываются.
- Ошибка первой страницы — «Не удалось загрузить треки. Проверьте соединение.» и
  «Повторить» (список пуст); «Не найдено» — 404. Ошибка следующей страницы — внизу
  «Не удалось загрузить ещё…» и «Повторить», загруженное остаётся.
- Пустой список — «Треков нет». Нажатие на трек строит очередь из загруженных
  треков списка и играет с него; источник в истории — исполнитель.
- Источники: десктоп `src/api/catalog.rs` (`fetch_artist_tracks`, `ARTIST_TRACKS_PAGE`),
  `src/ui/library/browse.rs` (`artist_tracks_page`), `docs/api/stage-7.md`.
  **На Android вживую не проверено**; проверить: приходит ли `pager.total`, что
  будет на странице за последней, у исполнителей с тысячами треков.

## Ошибки и крайние случаи (общие)

| Ответ | Что делаем |
|---|---|
| 401, 403 в коллекции | `UnauthorizedException` → сообщение «войдите заново» |
| 5xx, 429, сеть | «Не удалось загрузить», кнопка «Повторить» |
| Не JSON / не тот вид `result` | как ошибка загрузки |
| Пустой список | пустое состояние экрана |
| Количества не пришли | строка хаба без числа, хаб не ломается |

## Что не удалось подтвердить и что проверить вживую

- Эта спека не проверялась живыми запросами (токена у агента нет).
- Форма элемента `likes/albums` и `likes/artists` (обёртка или голый объект) —
  разбор принимает обе, но на живом ответе не видели.
- `music-history`: формат, `fullModelsCount`, привязка `itemId`.
- Совпадает ли число в хабе с официальным клиентом: «Плейлисты» = свои
  (без `kind` 3) + понравившиеся; «Альбомы» и «Исполнители» — длина
  разобранных списков.
- Полки (раздел 10): форма `landing-blocks/*` на Android (приходят ли
  `count`-порции, есть ли `description`, формат `releaseDate`), число
  элементов при `count=16/30/10`.
- 403 `ownerOtherwiseUserBindingError` на `likes/*` с cookie-токеном; с
  OAuth-токеном на десктопе не наблюдалось.

## Расхождения реализации со спекой (шаг 2)

- Отдельных запросов «только число» нет: количества альбомов и исполнителей на
  хабе берутся из длины списков `likes/albums?rich=true` и
  `likes/artists?with-timestamps=true` (один запрос на адрес). Списки
  сортируются по `timestamp`, свежие первыми.
- `brief-info`: если в нём ровно 9 альбомов и `counts.directAlbums` больше,
  альбомы дозагружаются из `direct-albums` (до 10 страниц по 100); сбой
  дозагрузки оставляет первые 9.
- `error` у альбома или исполнителя (даже при 200) — «Не найдено». Идентификаторы
  в адресе — только цифры (до 20), иначе запроса нет.
- Недоступные треки плейлиста и альбома показываются серыми; в очередь
  воспроизведения плеер их не берёт.

## История и «Недавнее»: как это устроено (шаг 3)

Десктоп (`src/ui/history.rs`, `src/ui/history_store.rs`) ведёт локальный журнал
прослушиваний (`LocalPlays`) и сливает его с ответом `music-history`
(`merge_days`), потому что сервер показывает прослушивания не сразу или не
показывает вовсе. Android переносит то же поведение:

- **Журнал.** Запись появляется, когда трек реально зазвучал (смена текущего
  трека, когда звук уже идёт, либо первый `onIsPlayingChanged(true)` после
  смены; пауза и возобновление не пишут повторно). Хранится: id, название,
  исполнители, альбом, uri обложки, длительность, `available`, контекст очереди
  (альбом, исполнитель, плейлист, волна, «Мне нравится», иное), день и время.
  Файл `filesDir/play_log.json`, не больше 300 записей (на десктопе 1000 за 30
  дней). Аудио и ссылки на поток не пишутся. Тот же трек за тот же день не
  дублируется: прежняя запись уходит, трек поднимается наверх. Битый файл или
  запись — пустой журнал. При выходе из аккаунта журнал очищается.
- **Слияние** (`mergeHistory`): локальные прослушивания встают в начало своего
  дня, свежие первыми, подряд идущие из одного контекста — одна группа; тот же
  трек в тот же день с сервера убирается; дня нет у сервера — он встаёт по
  дате. Отличие от десктопа: дни считаются по часовому поясу устройства, а не
  по UTC.
- **Сервер.** `GET /music-history?fullModelsCount=50`: не больше 30 дней и 300
  треков, треки без полной модели догружаются пачкой `POST /tracks`, треки без
  названия отбрасываются. Ошибка сервера при непустом журнале экран не
  ломает.
- **«Недавнее»:** до 6 последних альбомов и плейлистов из контекстов (серверных
  и локальных), без «Моей волны» и повторов. Число треков плейлиста и обложка
  берутся из списка плейлистов пользователя, если плейлист там есть;
  исполнитель альбома и обложка — из первого трека группы.
- **`play-audio` не отправляется** (это запись в аккаунт, решение за
  пользователем). Поэтому прослушивания с телефона в серверную историю
  Яндекса не попадают: на телефоне видна только локальная часть, а серверная
  показывает то, что играли в других клиентах. Следствие для аккаунта: в
  официальных клиентах и в «Моей волне» эти прослушивания не учитываются.

### Расхождения (шаг 3)

- Формат `music-history` пересказан по справке и на десктопе вживую не
  проверялся; на Android тоже.
- Дни локального журнала — по часовому поясу устройства, серверные даты — как
  пришли.

## Отправка прослушиваний (`play-audio`)

Решение пользователя (2026-11-12 для десктопа, распространено на Android):
Plastinka сообщает Яндексу о прослушиваниях, как официальный клиент. Это
согласованная запись в аккаунт, только она. Логика перенесена из нашего
`src/api/play_audio.rs` (`Tracker`, `PlayReport`) и `src/ui/library.rs`
(`report_begin`/`report_start`/`report_finish`); раздел «История» в
`docs/api/stage-9.md`. Код MarshalX не переносился.

- **Запрос:** `POST https://api.music.yandex.net/play-audio`, заголовки
  `Authorization: OAuth <токен>`, `X-Yandex-Music-Client`; тело —
  `application/x-www-form-urlencoded`.
- **Поля формы:** `track-id`, `album-id` (если известен), `from=plastinka`,
  `from-cache=false`, `play-id` (UUID v4 на каждый запуск трека), `uid`,
  `timestamp` (когда трек начался, RFC 3339 UTC с миллисекундами, например
  `2026-11-15T10:20:30.123Z`), `client-now` (когда отправлено, тот же формат),
  `track-length-seconds` (если известна), `total-played-seconds` и
  `end-position-seconds` (равны, целые секунды).
- **Сколько раз:** два сообщения на трек. Первое — когда пошёл звук (сыграно 0,
  один раз; перемотка и буферизация второго не дают). Второе — когда трек
  сменился, кончился или очередь доиграна: сколько сыграно (время, пока звук
  шёл, без пауз); доигранный до конца — вся длительность. Трек, который не
  зазвучал, не шлём. Для замены FckCensor (прямая ссылка из хранилищ) не шлём.
  Волна шлёт `play-audio` так же (кроме rotor-событий `waveFeedback`, они
  независимы).
- **Условия:** только после подтверждённого Плюса (`AccountHolder.allow` вызывается
  после `account/status` с Плюсом, при ошибке статуса или выходе —
  `clear()`), только с токеном; при выходе отложенные отправки отменяются.
- **Ошибки:** в фоне, не мешают воспроизведению, повторов нет; в лог — только
  id трека и код ответа, токена нет.
- **Не проверено вживую:** имена полей формы (по памяти, справка MarshalX),
  принимает ли сервер `from=plastinka`, нужен ли `play-audio` для волны, как
  быстро трек появляется в `music-history`.
- **Слияние с историей:** локальный журнал остаётся; `mergeHistory` убирает с
  сервера тот же трек в тот же день. Ограничение: день локального журнала — по
  часовому поясу устройства, серверный — как пришёл; у границы суток трек может
  показаться на двух днях.
