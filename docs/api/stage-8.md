# Этап 8: «Моя волна» (rotor) — спецификация API

Разведка — 2026-11-06. Источники: исходники крейта `yandex-music` 0.7.0
(`src/api/rotor/*`, `src/model/rotor/*`, `src/model/track/mod.rs`,
`src/model/landing/wave.rs`) — читали целиком; справка MarshalX и OpenAPI
acherkashin открыть не смогли (у агента нет доступа к вебу). Всё, что ниже
помечено **«по памяти»** или **«проверить вживую»**, взято из общих знаний о
поведении сервиса и не подтверждено ни крейтом, ни живым ответом. Живых
запросов к rotor агент не делал (нужен настоящий токен, а он агенту
запрещён). Код MarshalX и чужих клиентов не переносим.

Заголовки у всех запросов те же, что на этапах 2–7:
`Authorization: OAuth <token>`, `X-Yandex-Music-Client: YandexMusicAndroid/24023621`.
Хост `https://api.music.yandex.net`. Тело POST — JSON, `Content-Type:
application/json` (в отличие от `POST /tracks` и `dislikes/…`, где форма).
Ответ в обёртке `{"invocationInfo":{…},"result":…}` или `{…,"error":{…}}`.
Токен в адрес, тело и сообщения об ошибках не попадает.

## Итог

1. **Берём сессионный путь**: `POST /rotor/session/new`, затем
   `POST /rotor/session/{radioSessionId}/tracks` и
   `POST /rotor/session/{radioSessionId}/feedback`. Причины: (а) в крейте
   сессионный путь — основной (`create_session`, `get_session_tracks`,
   `send_station_feedback` тоже ходит на `rotor/session/…`), старый
   `GET /rotor/station/{id}/tracks` в крейте есть, но написан с ошибкой (см.
   «Расхождения»); (б) только сессия возвращает `radioSessionId`,
   `batchId`, объект `wave` (`idForFrom` — значение поля `from` в событиях) и
   параметры трека (`trackParameters`: `hue`, `energy`, `bpm`); (в) по
   общим знаниям, так работают современные клиенты, а старый путь оставлен
   для совместимости (**проверить вживую**).
2. Крейт `yandex-music` по-прежнему не подключаем (решение этапа 4). Запросы
   свои, на reqwest, разбор мягкий. Строгая модель крейта `Session` требует
   `batchId`, `pumpkin`, `terminated`, `sequence`, а `SequenceItem` —
   `trackParameters` с `bpm: u32`; у каждого `Track` обязательны `realId` и
   ещё несколько полей. Один неожиданный трек ломает весь ответ. Нам нужно
   разбирать каждый элемент `sequence[]` отдельно.
3. **Трек из волны разбирается нашей `parse_track`** (`src/api/tracks.rs`):
   вложенный `sequence[].track` — тот же объект, что в `POST /tracks`.
   Функция `pub(super)` в `api::tracks`, модуль `api::rotor` её уже видит,
   менять видимость не нужно.
4. Цвет для VibeColorizer: у трека в ответах волны **возможно** есть
   `derivedColors` (`average`, `waveText`, `miniPlayer`, `accent`) и
   `trackParameters.hue`. Не гарантировано (**проверить вживую**). План:
   брать `derivedColors.accent` или `average`, иначе `hue`, иначе считать
   среднее по уже загруженной обложке.
5. Звук не меняется: волне, как и любой очереди, плееру нужен только
   `track_id` через `queue::sound` (поток Яндекса, правила 1 и 7). Ничего,
   кроме JSON-метаданных, не читаем и не пишем на диск. Адрес потока в
   rotor-ответах не используется.
6. «Не нравится» — запись в аккаунт: отдельное решение пользователя
   (см. раздел «Не нравится»). Отзыв `skip` в волну аккаунт не меняет.

## `POST /rotor/session/new` — старт волны

- Тело (крейт `create_session.rs`; пример из его комментария):

  ```json
  {"seeds":["user:onyourwave"],"queue":[],"includeTracksInResponse":true,
   "includeWaveModel":true,"interactive":true}
  ```

  Крейт по умолчанию ставит `interactive: false`; в комментарии к методу —
  `true`. Что именно меняет флаг, неизвестно (по памяти: `true` включает
  обратную связь и адаптацию «живой» волны). Берём `true`, **проверить
  вживую**. `queue` при старте пуст (id:albumId прошлых треков нужны только
  для продолжения по уже играющему треку).
- `seeds`: для «Моей волны» одно значение `"user:onyourwave"`. Другие станции
  (жанры, исполнитель `artist:123`, плейлист и т. п.) — вне этапа.
- Ответ 200, поля, которые нужны нам (структура по крейту `session.rs`,
  значения придуманы по смыслу):

  ```json
  {"result":{
    "radioSessionId":"s_abc123…",
    "batchId":"b_def456…",
    "sequence":[
      {"type":"track","liked":false,
       "trackParameters":{"bpm":120,"energy":0.7,"hue":210.0,"userCollectionHue":0},
       "track":{"id":"29238706","realId":"29238706","title":"…","available":true,
                "durationMs":114330,"coverUri":"avatars.yandex.net/…/%%",
                "artists":[{"id":41052,"name":"…"}],
                "albums":[{"id":10101,"title":"…"}],
                "derivedColors":{"average":"#…","waveText":"#…","miniPlayer":"#…","accent":"#…"}}}
    ],
    "wave":{"name":"Моя волна","description":"…","idForFrom":"…",
            "seeds":["user:onyourwave"],"stationId":"user:onyourwave"},
    "acceptedSeeds":[…],"pumpkin":false,"terminated":false}}
  ```

  - `radioSessionId` — часть адреса всех следующих запросов. Только
    безопасные символы (буквы, цифры, `_`, `-`, `.`); иначе считаем ответ
    битым: значение попадает в адрес запроса (как `numeric_id` у числовых).
    Когда `radioSessionId` отсутствует (поле `Option` в крейте), волну
    запустить нельзя — «неожиданный ответ».
  - `batchId` — идентификатор текущей порции. Его же присылаем в событиях
    обратной связи для треков из этой порции. Меняется с каждой порцией.
  - `wave.idForFrom` — строка для поля `from` в событиях (в самой
    документации крейта «id_for_from»; по памяти выглядит как
    `radio-mobile-user-onyourwave-default`). Если `wave` нет — `from`
    не шлём или берём `"radio-mobile-user-onyourwave-default"` (**проверить
    вживую**).
  - `terminated: true` — сервер закончил сессию. Для «Моей волны» такого
    быть не должно; если пришло, показываем «Волна закончилась» и даём
    запустить снова.
  - `unknownSession: true` (в крейте `Option<bool>`) — сервер не знает такую
    сессию (она протухла): создаём новую через `session/new`.
  - `sequence[].type` — `"track"`; другие значения (по памяти, бывают
    рекламные вставки у бесплатных аккаунтов) пропускаем, это не наша
    забота: плеер играет только при подписке (правило 2).
  - `sequence[].liked` — трек уже в «Мне нравится» у пользователя. Нужен для
    значка сердца в плеере.
- Ошибки: 401/403 — `ApiError::Unauthorized`; 429/5xx — `Server`; прочее —
  `UnexpectedStatus`; нет `radioSessionId`/непонятный JSON — `InvalidResponse`.
  400 с телом `{"error":{"name":"validate",…}}` — битый запрос (баг нашего
  кода), показываем общую ошибку.
- Крайние случаи: пустой `sequence` (после фильтра недоступных) — «Волна
  пока не нашла треков. Попробуйте позже»; `available: false` у части
  треков — пропускаем при разборе в очередь, но при пустом остатке догружаем
  следующую порцию.
- Покрытие крейтом: **есть** `create_session` + `CreateSessionOptions`
  (все поля тела), модель `Session`. Не подходит: строгая модель (см.
  «Итог» п. 2).
- Источники: крейт (высокое доверие); поведение флагов — по памяти.

## `POST /rotor/session/{radioSessionId}/tracks` — следующая порция

- Тело (крейт `get_session_tracks.rs`):

  ```json
  {"queue":["29238706:10101","7019818:777"],"feedbacks":[]}
  ```

  - `queue` — id треков в формате `{trackId}:{albumId}`, что уже было в
    очереди (по крейту: «очередь идентификаторов»). Сколько отправлять:
    **по памяти**, клиенты шлют последние несколько уже выданных треков,
    чтобы сервер не повторял и продолжал контекст. Предлагаем: последние
    не более 5 id из уже полученных в сессии. Если у трека нет `albumId`,
    шлём только `trackId` (**проверить вживую**, принимает ли сервер).
  - `feedbacks` — события, которые можно приложить к запросу вместо
    отдельного `…/feedback` (в крейте — `Vec<StationFeedback>`). Мы шлём
    события отдельным запросом (см. ниже), здесь оставляем `[]`: меньше
    связанности и проще повтор.
- Ответ: тот же вид, что у `session/new` (`Session`): новый `batchId`,
  `sequence[]`, `radioSessionId` (может дублироваться). Новый `batchId`
  берём как текущий для следующих событий.
- Размер порции: **неизвестен**. По памяти — от 2 до 5 треков на запрос;
  заранее на число не рассчитываем. Дальше — «Догрузка» и «Дубликаты».
- Ошибки как у `session/new`; `unknownSession: true` или 400/404 на
  протухшую сессию — один раз создаём новую сессию (с `queue` из последних
  треков) и повторяем догрузку; второй сбой подряд — сообщение об ошибке.
- Покрытие крейтом: **есть** `get_session_tracks`. Не подходит: модель.
- Источники: крейт.

## Старый путь: `GET /rotor/station/user:onyourwave/tracks`

- Крейт `get_station_tracks.rs`: параметры `settings2=true` и `queue`
  (одно значение — id последнего трека, **по памяти** в старом формате
  без `:albumId`). Ответ: `StationTracks` — `id`, `batchId`, `pumpkin`,
  `sequence[]` (`type`, `track`, `liked`). Нет `radioSessionId`, нет `wave`,
  нет `trackParameters`.
- Ошибка в крейте: путь собирается как `…/tracks` + `?settings2=true` + затем
  `&queue=…`, причём `&queue` дописывается и без `settings2`: получается
  `…/tracks&queue=…` — битый адрес. Значение `queue` не кодируется.
- Обратная связь для него: `POST /rotor/station/{id}/feedback?batch-id=…`
  (по памяти; в крейте этого метода нет — `send_station_feedback` ходит на
  `rotor/session/…`). События те же (`radioStarted`, `trackStarted`,
  `trackFinished`, `skip`), но поля без `batchId`.
- **Не выбираем**: запасной вариант. Если живая проверка покажет, что
  сессионный путь для нашего клиента отвечает ошибкой, перейдём на старый и
  допишем этот раздел по результатам.

## `POST /rotor/session/{radioSessionId}/feedback` — обратная связь

- Тело (**подтверждено вебом**: MarshalX issue #589 и исходники клиента
  plavno 0.1.1 на docs.rs; крейт `yandex-music` сериализует иначе, см.
  «Расхождения»):

  ```json
  {"event":{"type":"trackFinished","timestamp":"2026-11-06T12:00:00.123Z",
            "from":"mobile-radio-user-onyourwave",
            "trackId":"29238706:10101","totalPlayedSeconds":114.3},
   "batchId":"b_def456…"}
  ```

  Ключ `batchId` — camelCase, рядом с `event`. `from` лежит внутри `event`
  (по OpenAPI acherkashin — поле события; пример значения
  `mobile-radio-user-onyourwave`; берём `wave.idForFrom`, если он пришёл).
  `timestamp` — строка RFC 3339 в UTC (пример `2023-06-06T13:33:00+00:00`,
  доли секунды допустимы; мы шлём `…Z` с миллисекундами).
  `totalPlayedSeconds` — только у `trackFinished` и `skip`.
- Типы событий (`event.type`): `radioStarted`, `trackStarted`,
  `trackFinished`, `skip` (названия из задачи этапа и по памяти; крейт тип
  не ограничивает, поле — строка). Возможно, бывают ещё `like`, `dislike`,
  `unlike`, `undislike` (**по памяти**, не проверено) — нам они не нужны:
  «нравится» ставит отдельный метод аккаунта.
- Поля по событиям (предлагаем):

  | Тип | `trackId` | `totalPlayedSeconds` | `from` | Когда шлём |
  |---|---|---|---|---|
  | `radioStarted` | нет | нет | `wave.idForFrom` | сразу после успешного `session/new`, один раз |
  | `trackStarted` | `id:albumId` | нет | да | когда трек реально начал играть (кнопка «Play» нажата, звук пошёл), не раньше |
  | `trackFinished` | `id:albumId` | сколько проиграно (≈ длительность) | да | трек доигран до конца сам |
  | `skip` | `id:albumId` | сколько проиграно | да | пользователь нажал «Следующий» (или сработал автопропуск плагина) до конца трека |

  `timestamp` — момент события, `Utc::now` в RFC 3339 (в проекте `chrono`
  может быть не подключён; формат можно собрать из `SystemTime`). По памяти
  старые клиенты слали число секунд с эпохи; крейт сериализует
  `DateTime<Utc>` как строку (**проверить вживую**, какой формат принимает
  сервер).
- **Минимально правильный набор**, чтобы волна подстраивалась:
  `radioStarted` один раз (`from` = `idForFrom`, `batchId` первой порции, без
  `trackId`); на каждый трек — `trackStarted`, затем либо
  `trackFinished`, либо `skip`. Всё остальное (включая `playedSeconds` — в
  крейте это поле названо «длительность трека», по смыслу, видимо, полная
  длина трека) необязательно. Нужно именно парное закрытие
  каждого `trackStarted`: без `trackFinished`/`skip` сервер не знает, понравился
  ли трек.
- Порядок при переключении: сначала `skip`/`trackFinished` для уходящего
  трека (с его `batchId`), потом — только когда следующий трек действительно
  начал играть — `trackStarted` для нового. Если пользователь закрыл
  приложение посреди трека — событие не шлём (не гарантируем и не ждём).
- Когда НЕ шлём `skip`: трек пропущен автопропуском ИИ (Slopless), пока он не
  успел заиграть (0 секунд) — это решение плагина, а не вкус пользователя,
  и в рекомендации влиять не должно. Но если ИИ-трек уже играет и
  пользователь сам нажал «следующий» — обычный `skip`. Если после
  автопропуска мы поставили «Не нравится» (по согласию) — см. ниже.
- Повтор трека (поведение мода PulseSync): волна играет тот же трек второй
  раз — это для сервера два отдельных `trackStarted` → `trackFinished` с тем же
  `trackId`. По памяти в моде повтор не шлёт ничего особенного. Предлагаем:
  повтор — обычная пара событий, без `skip`. **Не копируем код мода.**
- Ошибки: любой сбой обратной связи не прерывает воспроизведение и
  пользователю не показывается (максимум — тихая отметка в состоянии
  приложения). Событие, отправленное с 401/403, считается признаком того,
  что токен не действует — как любая другая ошибка, но обрабатываем её
  только через следующий основной запрос (догрузку), чтобы не выкидывать
  на вход из-за фоновой операции. События шлём в фоне, без ожидания ответа,
  в порядке создания (одна очередь), чтобы `trackStarted` не обогнал
  `skip`.
- Ответ 200: `{"result":"ok"}` (по памяти); крейт не читает тело
  (`request_unit`).
- Покрытие крейтом: **есть** `send_station_feedback`, но с замечаниями выше
  (плоский `batch_id`, `unwrap()` при сериализации в его коде — нам не
  важно). В нашем коде — свой запрос.
- Источники: крейт; полный набор типов и точные ключи — по памяти.

## «Не нравится» в волне

- Отзыв для сервера — событие `skip` (см. выше). Дополнительно можно
  записать трек в «Не нравится» аккаунта: `api::add_disliked_tracks`
  (`src/api/tracks.rs:158`, `POST /users/{uid}/dislikes/tracks/add-multiple`,
  форма `track-ids=<id>`), уже используется Slopless после согласия.
- Это **запись в аккаунт пользователя** (`dislikes` влияет на рекомендации и
  в других клиентах). Решение по интерфейсу — отдельная кнопка «Не нравится»
  в плеере только в режиме волны или нет — принимает пользователь, не
  агент. Кнопка должна: слать `skip`, ставить «Не нравится», переключать на
  следующий трек. Без согласия/кнопки автоматически ничего в аккаунт не
  пишем.
- Фальшивый токен: `add_disliked_tracks` с тестовыми хуками возвращает
  `Ok(())` без запроса (как сейчас).

## Догрузка очереди

- Порция из `session/new` — первая очередь. Дальше догружаем следующую
  порцию, когда в очереди волны **впереди текущего трека осталось не больше
  2 треков** (то есть начинаем запрос заранее, пока играет предпоследний;
  число подберём по размеру порции после живой проверки).
- Один запрос на догрузку одновременно: пока запрос идёт, второй не
  стартуем. Если порция пришла пустой (все недоступны/уже были) — пробуем
  ещё до 2 раз подряд, потом «Волна пока не нашла треков» (чтобы не
  зациклиться).
- Если пользователь прокликал «Следующий» быстрее, чем пришла догрузка, —
  плеер ждёт порцию, показывая «Загружаем волну…», а не останавливается
  молча.
- При ошибке догрузки играем то, что уже в очереди; когда очередь кончилась —
  ошибка с кнопкой «Повторить» (как у остальных экранов).
- Остановка: когда пользователь уходит из волны в обычный плейлист, волну
  закрываем без запросов (у сессии нет `DELETE`; она протухает сама).
  События обратной связи на выходе не шлём (кроме закрытия трека `skip`,
  если он играл).

## Дубликаты

- Сервер сам не должен повторять недавние треки, если в `queue` передать их
  id; на сервер полагаться не стоит.
- На своей стороне: в рамках сессии храним множество id уже полученных
  треков (до 500 последних, дальше вытесняем старые) и выкидываем из новой
  порции треки, что уже были в очереди или проигрывались. Намеренный «повтор
  трека» (поведение мода) этим не ограничиваем — он делается отдельным
  действием плеера, а не через порцию.
- Если после фильтра порция пуста — как в «Догрузке».

## `GET /rotor/account/status`, `GET /rotor/station/{id}/info`

- `rotor/account/status` (крейт: `get_station_account_status`, модель
  `AccountStatus`) — тот же вид ответа, что `account/status`, но «глазами»
  rotor. Нам **не нужен**: подписку (правило 2) мы проверяем уже сделанным
  `fetch_status` до создания плеера.
- `rotor/station/{id}/info` (`get_station`) — описание станции и её
  **текущие настройки** пользователя. Возвращает список `Rotor`:
  `station` (`id`, `name`, `idForFrom`, `restrictions`, `restrictions2` —
  допустимые значения настроек), `settings`, `settings2` (`language`,
  `diversity`, `mood`, `moodEnergy`, `energy`), `adParams`,
  `rupTitle`, `rupDescription`. Без настроек волны не нужен. Название и
  описание волны берём из `wave.name`/`wave.description` ответа
  `session/new` (если там есть), иначе — фиксированный текст «Моя волна».
- Также есть `rotor/stations/dashboard` и `rotor/stations/list` (`get_stations_dashboard`,
  `get_all_stations`) — каталог других станций. Вне этапа.

## Настройки волны (`settings2`) — только справка

Не внедряем. Что есть по крейту (`model/rotor/mod.rs`, `restrictions.rs`):

- `language` — язык треков (значения вроде «любой», «русский», «иностранный»;
  конкретные ключи — в `restrictions2.language.possibleValues`).
- `diversity` — «Незнакомое / Любимое / Популярное» и «по умолчанию»
  (`restrictions2.diversity.possibleValues`).
- `mood` — шкала `min..max` (`StationDiscreteScale`), `moodEnergy` —
  «настроение» (`active/fun/calm/sad`), `energy` — число.
- Изменение — отдельным запросом (по памяти
  `POST /rotor/station/{id}/settings3`); в крейте метода нет. Не используем.

## Как трек лежит в ответе и чем отличается от нашего

- `result.sequence[]` → объект `{type, liked, trackParameters, track}`;
  настоящий трек — во вложенном `track`. Он того же вида, что элемент
  `result[]` в `POST /tracks`, поэтому наш `parse_track` (id, title,
  version, artists с id, albums[0], durationMs, available, coverUri,
  contentWarning) разбирает его без изменений. Поля `real_id`, `og_image`
  и пр. нам не нужны.
- `track.albums` в волне — как в `POST /tracks`: обычно один альбом; нужен
  `albums[0].id` для `trackId` вида `id:albumId`. Нет альбома → шлём только
  `id` (**проверить вживую**).
- Что добавляем сверх `api::Track`: у элемента волны есть `liked`
  (значок «нравится»), `trackParameters` (`hue`, `energy`, `bpm`) и
  `batchId` порции. Предлагаем отдельный тип `WaveTrack { track: Track,
  liked: bool, hue: Option<f32>, accent: Option<…>, batch_id: String }`, а
  `Track` не трогать.
- Различия моделей: крейтовый `Track` — отдельная строгая структура
  (`real_id` обязателен, `albums` — полный `Album`); мы её не берём.
  `available` у нас — «только явное `true` и без `error`», как везде.
  Недоступные треки из порции выбрасываем сразу (не заглушки: порядок
  волны не важен, как у списка «Мне нравится»).

## Цвета (VibeColorizer)

- Крейт описывает у `Track` необязательное `derivedColors` с полями
  `average`, `waveText`, `miniPlayer`, `accent` (строки; формат по
  названию — `#RRGGBB`, **проверить вживую**, нет ли `rgba(…)`). Поле
  необязательное, в модели помечено `#[serde(default)]`, то есть в части
  ответов его нет.
- В других ответах крейта есть `landing/wave`: `colors.average`,
  `colors.waveText`, `agent.cover.color` — это цвета карточек волны на
  главной (landing), а не треков.
- `averageColor` у альбома/трека в крейте **нет**.
- `trackParameters.hue` (число, в крейте `f32`; **по памяти** градусы 0–360)
  — оттенок трека; пригодится как запасной вариант.
- План для VibeColorizer: порядок выбора — `derivedColors.accent` →
  `derivedColors.average` → цвет из `hue` → среднее по уже загруженной
  обложке (код проекта уже грузит обложку; сеть для цвета не нужна).
  Если живая проверка покажет, что `derivedColors` в rotor-ответах не
  приходит, остаётся считать цвет самим из обложки.

## Тестовый хук `PLASTINKA_TEST_ROTOR`

Формат — как у `PLASTINKA_TEST_CATALOG`/`PLASTINKA_TEST_LIKES`
(`api::test_hook`): работает только в отладочной сборке, только для токена из
`PLASTINKA_TEST_TOKEN` (иначе ошибка `TestHook`), пустое значение выключает.
Вместо запросов к сервису разбираются готовые ответы; события обратной связи
в сеть не уходят (запрос не строится), а запись «Не нравится» не пишется
(уже так у `add_disliked_tracks`). Имена:

| Имя | Что подменяет |
|---|---|
| `sample` | `session/new` — 5 треков (в том числе недоступный и без обложки); `tracks` — ещё 2 порции по 5, потом пустая порция («Волна закончилась»). Треки собираются по id так же, как в `PLASTINKA_TEST_CATALOG`, чтобы работали плагины |
| `endless` | каждая догрузка отдаёт 5 новых треков с возрастающими id (проверка очереди и долгой сессии) |
| `empty` | `session/new` отвечает пустым `sequence` («Волна пока не нашла треков») |
| `duplicates` | догрузка повторяет треки, что уже были в сессии (проверка дедупликации) |
| `slow` | ответы через 1,5 с (видно «Загружаем волну…», можно уйти со страницы) |
| `expired` | первый `tracks` отвечает `unknownSession: true`, затем сессия создаётся заново |
| `new-503`, `new-401`, `new-broken` | старт волны падает: сервер недоступен / токен не принят / битый JSON |
| `tracks-503` | старт проходит, догрузка падает (играем остаток, потом «Повторить») |
| `feedback-503` | обратная связь возвращает ошибку; воспроизведение не страдает |
| `colors` | у треков заполнены `derivedColors` (и есть треки без них): проверка VibeColorizer и запасного расчёта по обложке |

Проверить, что отправлено: события обратной связи в хуке складываются в
память и доступны юнит-тестам (не выводятся в консоль и не пишутся в файл).

## Расхождения между источниками

Сверка лида по вебу 2026-11-06 (MarshalX #589, plavno 0.1.1, OpenAPI
acherkashin; код не переносили). Подтверждено: `batchId` camelCase рядом с
`event`; `from` внутри `event`; `timestamp` RFC 3339 UTC; `totalPlayedSeconds`
только у `trackFinished`/`skip`; `skip`/`trackFinished` прошлого трека идут до
`trackStarted` следующего; `session/new` с `seeds`, `includeTracksInResponse:
true`, `interactive: true` (мы дополнительно `includeWaveModel: true`, отсутствие
`wave` переживаем); `…/tracks` с телом `{"queue":[…]}`, куда по #589 входит
текущий трек (шлём последние не больше 5 `id:albumId`, текущий включительно);
`unknownSession: true` — сессия протухла. Старый `POST
/rotor/station/{id}/feedback` берёт `batch-id` в query (у `radioStarted` его
нет) — только справка. Пометки «по памяти» выше для этих пунктов
устарели. Остаётся «проверить вживую»: размер порции, `derivedColors`,
поведение протухшей сессии.

- **Старый и новый путь.** Крейт реализует оба, но старый — с ошибкой в
  адресе (см. выше). Современные клиенты, по памяти, ходят на сессионные
  методы.
- **Обратная связь.** Крейт шлёт события на `rotor/session/{id}/feedback`,
  а не на `rotor/station/{id}/feedback`, хотя метод и поле называются
  «station». Старый путь с `?batch-id=…` в крейте не реализован. Ключ
  `batch_id` (сериализатор крейта) против `batchId` (по памяти) — не
  согласуются.
- **Поля времени.** `timestamp` — RFC 3339 строка (крейт) против числа
  секунд (по памяти в старых клиентах).
- **`playedSeconds`.** В крейте поле `track_length` сериализуется как
  `playedSeconds`, а `total_played` — как `totalPlayedSeconds`:
  названия не сходятся со смыслом.
- **`interactive`.** По умолчанию `false`, в комментарии крейта — `true`.
- **`queue`.** В старом пути — один id, в сессионном — список `id:albumId`.
- **Строгость моделей.** `Session` и `Track` в крейте падают на
  отсутствии полей; реальные ответы — нет гарантий (в отличие от `Track` в
  `POST /tracks`, который мы уже разбираем мягко).
- **Источники MarshalX/OpenAPI** не открывались; все «по памяти» — гипотезы.

## Что проверить вживую

Нужен настоящий аккаунт с Плюсом; делает пользователь (агенту токен
запрещён). Проверять можно через временную консольную команду или через
окно.

1. `session/new` с `interactive: true` и `false`: приходят ли `radioSessionId`,
   `batchId`, `wave.idForFrom`, `sequence[]`; сколько треков в порции;
   есть ли `derivedColors` и `trackParameters.hue`, формат цвета.
2. `…/tracks` с `queue` из последних 1, 3 и 5 треков в форматах `id:albumId`
   и просто `id`: не повторяются ли треки, сколько их в порции.
3. `…/feedback`: принимает ли сервер ключ `batchId` (и `batch_id`),
   формат `timestamp`, нужен ли `from`, отвечает ли 200 на пропуск
   `radioStarted` без `trackId`.
4. Адаптируется ли волна на практике: после серии `skip` исполнитель
   перестаёт попадаться; после `trackFinished` — продолжается похожее.
5. Поведение протухшей сессии (долгая пауза): какой код/поле (`unknownSession`,
   400, 404) вернётся.
6. Рекламные вставки (`type` не `track`) на аккаунте с Плюсом.
7. Есть ли у части треков из волны `available: false` и как часто.
8. Старый путь `GET /rotor/station/user:onyourwave/tracks` — отвечает ли
   вообще (нужен только как запасной).

## «Нравится»: поставить и снять

Сердце в окне — запись в аккаунт по явному нажатию (решение пользователя,
отдельного согласия не нужно).

- `POST /users/{uid}/likes/tracks/add-multiple` — поставить;
  `POST /users/{uid}/likes/tracks/remove` — снять. Заголовки как везде:
  `Authorization: OAuth <token>`, `X-Yandex-Music-Client`.
- Тело — форма (не JSON): `track-ids=<id>[,<id>…]`, каждый элемент `id` или
  `id:albumId` (так делает и крейт: `api/track/add_liked_tracks.rs`,
  `remove_liked_tracks.rs`, поле `track-ids`, значения через запятую). Мы
  шлём `id:albumId`, если альбом известен. Идентификаторы проверяются до
  отправки (число 1…`i32::MAX` или UUID, альбом — цифры); непохожий —
  запрос не уходит.
- Ответ: `{"result":{"revision":N}}` (крейт читает `revision`). Нам номер
  версии не нужен: список в окне обновляется сразу.
- Ошибки: 401/403 — токен не действует (вход заново), 429/5xx — «сервис
  временно недоступен», сеть — сообщение сети; все через `check_status`.
  Повторная постановка уже лайкнутого и снятие неотмеченного, по общим
  знаниям, не ошибки (**проверить вживую**).
- Покрытие крейтом: есть (`add_liked_tracks`, `remove_liked_tracks`), но
  крейт не подключён, запрос свой: `api::add_liked_tracks` и
  `api::remove_liked_tracks` в `src/api/tracks.rs`. С фальшивым токеном
  (`PLASTINKA_TEST_TOKEN`) запрос не отправляется, как у `add_disliked_tracks`.
- Окно: оптимистичное обновление, откат и сообщение при ошибке, 401 — на
  вход; пока запрос по треку идёт, повторные нажатия по нему игнорируются.

## Как окно использует rotor (шаг 4)

- Старт: `start_wave`, затем событие `radioStarted` (с `batchId` первой порции и
  `from`). Очередь `ListKey::Wave` растёт по мере догрузки (`fetch_wave_tracks`
  с последними `QUEUE_LEN` id, текущий включительно), повторы отсекаются по
  последним 500 id сессии, пустая порция повторяется не больше двух раз.
- `unknownSession` — один раз создаётся новая сессия (снова `radioStarted`).
- События идут по одному, в порядке возникновения (следующее — после ответа на
  предыдущее): `trackStarted` когда звук реально пошёл; `trackFinished` по
  концу трека (`totalPlayedSeconds` — длительность трека); `skip` — «Следующий»,
  «Не нравится», «Предыдущий», другой трек или другой список (`totalPlayedSeconds`
  — позиция плеера). `skip` и `trackFinished` только после `trackStarted`.
  Повтор трека — новая пара. Ошибки обратной связи не показываются.
- «Не нравится»: `skip`, `POST /users/{uid}/dislikes/tracks/add-multiple`
  (`api::add_disliked_tracks`, настоящему треку, не подмене) и следующий трек.
  Сердце у лайкнутого трека убирается локально: сервер, по общим знаниям, сам
  снимает «Нравится» при «Не нравится» (**проверить вживую**).

## Цвета для VibeColorizer (шаг 5)

Живого ответа с `derivedColors` по-прежнему нет (проверить вживую). Окно
берёт: `derivedColors.accent` → `derivedColors.average` →
`trackParameters.hue` → средний цвет большой обложки (600 px, считается один
раз при подготовке картинки, `Big.average`) → акцент. Цвет приводится к
читаемому на чёрном (светлота 0,42–0,68, у цветных насыщенность не ниже 0,35;
серый остаётся серым). Сеть для цвета не нужна: обложка уже в кэше. Большая
обложка запрашивается, только если в ответе нет ни цвета, ни оттенка.
